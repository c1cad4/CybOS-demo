# cybOS Resilience Stack: Offline Atlas, Radio Comms, and RF Lab

The goal is to make cybOS useful when internet services are unavailable: local maps and imagery, offline navigation, resilient communications, and lawful radio-signal awareness. These are separate capabilities with explicit hardware and data-source status, not one fictional "apocalypse mode".

## Current implementation status

### Stage 1 — local MBTiles archive inspection (in progress)
- The native UI has an **Offline Atlas** page reachable from the left rail and search.
- It accepts a local `.mbtiles` path, opens the SQLite database read-only, reads the standard `metadata` table, and verifies that the `tiles` table contains at least one tile.
- The report shows archive name, format, tile count, zoom range, bounds, center, and file size. The entered path and last inspection status are stored in local cybOS settings.
- A first raster preview reads a 3×3 neighborhood around the archive center from local MBTiles rows and decodes PNG/JPEG tiles without requesting network resources. It uses the archive center or bounds and an available zoom level; it is a preview, not a full pan/zoom map renderer.
- MBTiles TMS row numbering is converted to slippy-map Y coordinates for lookup. Tiles that are absent or cannot be decoded are shown as blank cells.
- No network access is needed to inspect or preview an existing local archive. No automatic map download is performed.

**Not implemented yet:** native file picker/import flow, interactive pan/zoom, vector-tile styling, region download packs, GNSS integration, saved waypoints, routing, satellite imagery layer management, and automated offline-operation tests. The current preview must not be labelled a complete offline navigation system.

## 1. Offline Atlas

### Intended capabilities
- Open local vector/raster map packages with no internet connection.
- Import MBTiles archives and display their metadata, geographic bounds, zoom range, and size.
- Maintain saved places, shelters, water points, farms, medical facilities, routes, and user-defined waypoints.
- Plan routes against locally available road/trail data; show clearly when routing data is missing or stale.
- Layer satellite/aerial imagery under roads and labels when a legally obtained local imagery package exists.
- Download selected regions and zoom levels before going offline, with estimated disk-space requirements, progress, pause/resume, checksums, and an offline-ready verification.
- Import/export GPX and GeoJSON; export a compact field pack for another cybOS device.
- Work without network access after the map package has been downloaded.

### Proposed implementation
- Treat MBTiles as an initial raster/vector tile container. The Rust mbtiles crate provides MBTiles database operations; first evaluate read-only access and license/API fit before adding it to the dependency graph.
- Keep map storage behind a provider trait so MBTiles, local folders, and future tile formats do not leak into the UI.
- Separate map rendering, tile storage, route graph, GNSS receiver input, and optional online downloads.
- Use offline routing data (for example, a region-specific OpenStreetMap extract and a compatible routing graph) separately from imagery tiles. Tiles alone do not provide turn-by-turn routing.
- GNSS/GPS location is not generated by offline maps: a device still needs a functioning GNSS receiver and a usable satellite fix. If unavailable, support manual position and last-known-position with a visible timestamp/accuracy warning.
- Satellite imagery must be downloaded from sources whose terms permit offline caching/redistribution; retain source, capture date, attribution, license, and coverage metadata. Never imply imagery is current when it is historical.

### Candidate references
- MBTiles Rust crate: https://crates.io/crates/mbtiles
- SAS.Planet source: https://github.com/sasgis/sas.planet.src
- MapTilesDownloader: https://github.com/AliFlux/MapTilesDownloader

These are references to evaluate, not dependencies to copy blindly. Tile-provider terms, API limits, attribution, licensing, and platform compatibility must be checked before shipping a downloader.

## 2. Resilient communications

### Intended capabilities
- Local peer-to-peer text messaging over LAN/Wi-Fi when available, with store-and-forward for peers that reconnect later.
- An explicitly separate radio gateway adapter for supported external radio/modem hardware; show whether a message is local-only, queued, transmitted, delivered, or acknowledged.
- Voice-room integration where a network exists, with a clear status showing that ordinary Mumble voice service is IP-based and is not itself a long-range radio.
- Message signing, peer identity verification, and end-to-end encryption for supported digital peers. Do not describe a channel as encrypted unless that specific transport and endpoint path has actually been verified.
- Compact emergency message format: sender ID, timestamp, expiry, message type, optional coordinates, and integrity check. Coordinates are opt-in and must be visible before sharing.
- Queue and export unsent messages for transfer by a user-selected offline method.

### Design constraints
- Mumble (https://github.com/mumble-voip/mumble) is a useful reference for low-latency voice over IP, not a replacement for a radio transceiver or radio modem.
- Radio transmission requires compatible hardware, a supported modem/codec, antenna, and correct band/power settings. The UI must not claim "radio range" or "transmitted" based only on a local send action.
- Frequency allocation, licensing, power limits, encryption rules, and emergency-use restrictions vary by jurisdiction. The app should provide region-specific compliance reminders and must not implement jamming or interference.
- Keep digital chat, voice over IP, and RF transmission as distinct transports with explicit status and capability checks.

## 3. Radio Spectrum / Signal Lab

### Intended capabilities
- Detect supported SDR hardware and show connection, frequency range, sample rate, and gain.
- Show spectrum and waterfall, tune a user-entered frequency, and scan only user-authorized frequency ranges at conservative configurable rates.
- Record IQ samples or audio only after explicit user action; attach timestamps, device settings, and file metadata.
- Provide signal-strength trends and basic modulation/bandwidth observations, where supported.
- Offer a safe import path for previously recorded IQ/audio files for offline analysis.
- Separate reception/analysis from transmission. Transmit controls must be absent unless a supported device, legal band plan, and deliberate transmit workflow are configured.

### Candidate references
- SDRangel: https://github.com/f4exb/sdrangel — broad SDR receiver/transmitter and spectrum-analysis application.
- Gqrx: https://github.com/gqrx-sdr/gqrx — SDR receiver and FFT/spectrum tool with hardware-specific dependencies.
- URH: https://github.com/jopohl/urh — universal radio hacker, useful as a reference for analyzing and demodulating recorded radio signals.
- Mumble: https://github.com/mumble-voip/mumble — IP voice communications reference.

Evaluate these as optional companion applications or interoperability targets first. Their different languages, GUI frameworks, licenses, device dependencies, and platform support make directly embedding their entire codebases into the Rust/egui app a separate engineering project.

## 4. Reliability and safety requirements

- Every capability reports one of: READY, OFFLINE-READY, DEVICE REQUIRED, DATA MISSING, PERMISSION REQUIRED, or ERROR.
- Offline-ready means tested with network interfaces disabled; a downloaded map alone is not proof that routing, GPS, search, or voice works offline.
- Never fabricate GPS coordinates, satellite imagery, signal detections, message delivery, or coverage.
- No hidden microphone recording, automatic transmission, jamming, or interception of private communications.
- Keep all logs local by default; make export/share explicit and show what is included.
- Include checksums, data provenance, storage estimates, stale-data warnings, and a recovery/export path.

## 5. Delivery order

1. **Offline Atlas foundation:** local map library, MBTiles metadata inspection, offline status, saved waypoints, import/export.
2. **Map display:** tile reader/rendering, layer controls, coordinate display, scale, attribution and source date.
3. **Pre-download packs:** bounded region/zoom selection, provider policy checks, resumable download and offline verification.
4. **GNSS integration:** device/OS location abstraction, last fix timestamp, accuracy and manual fallback.
5. **Offline routing:** region-specific road/trail graph, route planning, GPX import/export and missing-data warnings.
6. **Radio/communications capability inventory:** detect OS audio/network devices and supported SDR hardware; do not pretend unsupported devices work.
7. **Local store-and-forward text:** queue, signatures, peer identity verification and encrypted peer transport.
8. **Radio interoperability prototype:** first support one documented, legal hardware/modem path with end-to-end status reporting.
9. **Spectrum viewer:** hardware adapter, FFT/waterfall and recorded-sample analysis.
10. **Voice integration:** evaluate Mumble interoperability separately from radio hardware integration.

## Capability boundary and release gate

This file is the roadmap and architecture specification, not proof that a capability is shipped. At present, cybOS includes the first-stage local MBTiles inspector and a small raster-tile preview described at the top of this document. Full offline map interaction, GNSS, routing, region-pack downloads, radio hardware transmission, and SDR spectrum scanning remain unimplemented until each is separately delivered and tested on target hardware. Do not label a planned or adapter-ready stack as active, and do not report a message as delivered or a device as detected without an observed result.
